# Stage 7 Image Editing and Asset Lifecycle Design

> Status: Approved for implementation
> Date: 2026-08-23

## Goal

Add image insertion and image-asset replacement to the existing headless
editing model without moving binary storage, browser APIs, or asynchronous
storage concerns into `EditorEngine`.

This slice covers the JSON document transaction, the asynchronous editor
controller boundary, asset identity, reference cleanup, and failure behavior.
PPTX media/relationship/`p:pic` writeback and the UnoCSS asset-management UI
are separate follow-up slices.

## Boundaries

### `@ppt4ai/engine`

The engine remains synchronous and headless. It receives clone-safe commands
and atomically updates the document, selection, and patch history. It does not
call `AssetAdapter`, decode image bytes, inspect MIME data, or choose screen
coordinates.

The engine adds these commands:

- `insertImage`: insert one supplied `ImageElement` into a target slide and
  register its supplied `AssetMetadata`.
- `replaceImageAsset`: replace the asset reference and metadata for an existing
  image element while preserving the element's identity and visual geometry.

The commands validate the resulting document before recording a history entry.
An invalid command throws without changing document, selection, or history.

`insertImage` accepts a complete clone-safe image element, asset metadata, and
target slide ID. The element ID and asset ID must be unique in the current
document. The new element is appended to the target slide's `elementIds` and
becomes the only selected element. Its bounds are supplied in EMU by the
caller; the engine does not apply a viewport or pixel layout policy.

`replaceImageAsset` accepts an image element ID and a complete replacement
asset metadata record. It keeps the image element ID, bounds, z-order, and all
existing transform, crop, mask, and effect fields, changing only `assetId`
and the corresponding asset metadata. The replacement asset ID must differ
from any unrelated asset ID in the document. The target element must be an
image and the replacement metadata ID must match the new reference.

Both commands create one patch/inverse-patch history entry. Undo and redo
restore the complete document metadata and element references, including
assets that were removed or restored because of reference counting.

### `@ppt4ai/editor`

The editor exposes an asynchronous image asset controller around the
synchronous engine. The controller accepts image bytes, MIME type, optional
filename, and the caller's EMU bounds for insertion; replacement accepts an
existing image element ID instead of bounds. It performs the following order:

1. Validate supported bitmap MIME and decode enough metadata to determine
   pixel dimensions.
2. Generate an asset ID through an injected `assetIdFactory`.
3. Call `AssetAdapter.put(assetId, bytes, metadata)`.
4. Dispatch the corresponding synchronous engine command only after `put`
   succeeds.

The controller uses the existing shared bitmap MIME and dimension parsing
logic. It does not duplicate format-specific parsers in the UI layer. The
controller never mutates the document directly.

On input validation or adapter failure, the document remains unchanged and no
engine history entry is created. If `put` succeeds but engine dispatch fails,
the controller returns the written asset ID as an orphan so the host can later
collect it. It does not attempt an automatic asynchronous delete.

The controller returns the resulting `EngineState` on success and exposes
orphan IDs on a failed operation that may have written bytes. The existing
`EditorEngine.dispatch()` signature remains synchronous for all current and
headless consumers.

## Asset lifecycle

`document.assets` is metadata owned by the current document. An asset is live
when at least one image element in the document references its ID. After an
insert or replacement, metadata with zero current-document references is
removed from `document.assets`. This cleanup is part of the same synchronous
engine transaction as the element change.

Reference cleanup does not delete adapter bytes. Adapter storage is owned by
the host and may outlive the current document for undo/redo, imported source
packages, autosave snapshots, or other documents. Hosts may use orphan IDs
reported by the controller and their own storage/index policy to perform
explicit garbage collection.

An asset ID is unique within a document. IDs are generated by an injected
factory so tests, hosts, and persistence layers can choose deterministic
namespaces. The first implementation does not content-hash or deduplicate
identical bytes; every successful insertion or replacement receives the
factory's unique ID.

## Error and consistency rules

- Unsupported MIME, malformed image bytes, invalid dimensions, invalid EMU
  bounds, missing slide, duplicate IDs, and missing replacement targets are
  rejected before a document mutation is committed.
- Adapter `put` is awaited before dispatch; a rejected `put` leaves the engine
  untouched.
- A dispatch failure after a successful `put` reports an orphan ID and leaves
  the engine state as it was before the attempted command.
- All command payloads and stored metadata are `structuredClone`-safe.
- Existing undo/redo semantics remain synchronous and do not depend on adapter
  availability or adapter deletion.
- Existing image transform, crop, mask, and effect fields are preserved during
  replacement, even if the new image has different pixel dimensions.

## Testing

Engine tests cover insertion, replacement, atomic validation, selection,
slide ordering, asset reference cleanup, and undo/redo restoration. Controller
tests cover MIME/dimension validation, adapter call ordering, adapter failure,
dispatch failure with orphan reporting, injected IDs, and clone-safe payloads.
Existing image importer, SceneGraph, Canvas, thumbnail worker, boundary,
typecheck, build, and full test suites remain required.

No Element Plus dependency, DOM dependency, Canvas dependency, or new runtime
dependency enters `@ppt4ai/model` or `@ppt4ai/engine`.

## Explicitly deferred

- PPTX media part, relationship, and `p:pic` package writeback.
- Asset browser, upload controls, replacement UI, and other UnoCSS surfaces.
- Binary deletion from adapters and cross-document storage garbage collection.
- Content-addressed deduplication.
- Crop or transform editing controls.
